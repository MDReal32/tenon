## Why this way

I left `dist/` out of `.gitignore`, although the plan's list named it. In [the repository layout](../../../06-project/00-repository-layout.md), the root `dist/` holds the launchers for npm, PyPI, Homebrew and winget, which are source that DevOps writes and git must track. Both an unanchored `dist/` and an anchored `/dist/` would ignore that folder, so the first launcher task would find its files silently left out of git. No TypeScript package exists yet that builds into a `dist/` of its own. The task that adds the first one can ignore that package's output by its own path, which DevOps then adds.

I anchored `target/` to the root as `/target/`. Cargo writes its build output only at the workspace root, since every crate shares the root workspace's target directory. An unanchored `target/` would also hide any source folder named `target` deeper in the tree, such as a `src/target/` module in a crate. That is a plausible name in a generator like Tenon, where a generation target is a domain word. I anchored `/.nx/` for the same reason. Nx keeps its local state only at the workspace root. Ignoring the whole folder, rather than Nx's own list of subfolders, also covers any subfolder a later Nx adds. That is safe because this workspace installs Nx as a dev dependency and has no `.nx/` file to track, such as the wrapper that a `.nx` installation commits. `node_modules/` stays unanchored, since nested workspaces get their own `node_modules/`.

I kept Yarn's documented `.yarn/*` block whole instead of ignoring only `install-state.gz`. That covers the cache and the other local state Yarn may write, while patches, plugins and a checked-in release stay trackable, and the block can be checked against Yarn's docs at a glance. `.pnp.*` is part of that block. It ignores nothing while `.yarnrc.yml` sets the `node-modules` linker, but it stops a `.pnp.cjs` from being committed by accident if the linker ever changes. I added `*.tsbuildinfo` because no one ever wants TypeScript's incremental build state tracked, and having it already in place spares the first TypeScript task a separate DevOps step for it. `Cargo.lock` stays out of `.gitignore`: once a crate exists, Cargo writes it and the dev role commits it.

I dropped `-diff` from the lockfiles. The pull request size rules in [the departments overview](../../../departments/README.md) ask only for `linguist-generated`. That mark is enough to make GitHub collapse the file in a PR's diff and leave it out of the size and the language stats. `-diff` goes further: it makes git treat the lockfile as binary, so `git diff`, `git show` and `git log -p` print only "Binary files differ". Every department review reads changes through those commands, and the rules give a dependency bump its own PR, where the lockfile diff is the thing to review: which versions changed, and whether a dependency arrived that nobody asked for. Hiding that diff would cost the supply-chain check more than the noise it saves. `-diff` would also break a patch that carries a lockfile change, since `git format-patch` leaves the binary part out unless it gets `--binary`.

In the review, I made the analytics prompt a finding and kept the other observations as notes, and the line between them is whether the change can fix it now, inside the plan. The prompt changes a tracked file on a clean clone, which is the reproducibility the review checks, and one line in a file this change adds fixes it. I named `false` rather than leaving the value open, because the plan already turned Yarn's telemetry off, and either value stops the rewrite. If the owner prefers `true`, that passes the finding just as well.

The `.env` behaviour is a note, not a finding. Nx 24.0.6 loads the root `.env`, `.env.local` and `.local.env` into its own process at start-up, in `dist/bin/workspace-env.js`, with no switch. Unless `NX_LOAD_DOT_ENV_FILES=false` is set, it also passes them, with `.env.<target>` and the other names in `dist/src/tasks-runner/task-env-paths.js`, into every task's environment. It also sets `process.report.reportOnFatalError`, and Node's fatal-error report, which holds the process environment, lands in `.nx/workspace-data`. The handbook keeps project secrets in the root `.env` and lets only DevOps read it. Once that file holds a value, every `yarn nx` task any role runs would carry it, a crate's `build.rs` and its dependencies' build scripts included, and a task that prints its environment would put it in a transcript. Nothing leaks today, since this checkout has no `.env` or `.env.example`, and the change reads no variable. Fixing it means choosing between options the plan and the design leave open: setting `NX_LOAD_DOT_ENV_FILES=false` wherever Nx runs, though no tracked file can set it, or keeping secrets under a name Nx doesn't load, which changes the handbook's rule. That is a choice for the owner, so I didn't turn it into a finding with a fix of my own. The `.gitignore` lines that ignore `.env` and `.env.*` predate this change and don't cover `.local.env`, `.<target>.env` or `.<target>.local.env`, which Nx also reads. That goes into the same question, since this change didn't touch those lines.
