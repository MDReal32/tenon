# The Assistant and the PM session, written as a rule change

[#81](https://github.com/MDReal32/tenon/issues/81) splits the owner's main session in two. Until now every department run happened inside the session the owner chatted with, so the owner could not talk to it while the pipeline ran. The owner's fix is the Assistant, the owner's chat session, which stays free to talk, and a PM session of its own that runs the pipeline, started by the Assistant and never asking the owner anything in chat. The owner wanted this as a workspace rule or a part of the structure, not a department. This is HR's write step on the rule-change route, under the [departments](departments.md) job, continuing [HR's role-effort handoff](2026-11-13-hr-policy-role-effort.md), the last rule change HR wrote. A second assignment on the same PR then asked HR to fix the five findings of the fresh HR run's owner review, as the second attempt of the write step, and a third asked it to fix the one finding of the second owner review, as the third attempt. A fourth asked it to fix two of the three clashes the Architect reviewer's rule review found. A fifth asked it to rewrite what the owner's two answers of 2026-11-15, given in chat to the Assistant and posted on the issue, settle. A sixth asked it to fix the one finding of HR's fourth owner review and the three clashes of the Architect reviewer's second rule review, so this handoff covers all six.

## Why this way

The model check is the one place where PM's account and the coordinator's rules disagreed. The account had a PM session on the wrong model say so and carry on, while the coordinator's notes had it ask for `/model` and stop. The stop wins. HR's rules forbid loosening the model check unless the owner's note asks for it in its own words, and #81 only asks who sets PM's model. Carrying on would also break the handbook's start-up check, which says a mismatch means no work. What changes is only where the report goes: to the Assistant, in the first line, since PM no longer asks the owner directly. PM's account also says it posts its questions in BA's plain-language shape with a suggested answer each. That stayed out, because the issue asks only that questions go on the issue, and the coordinator's issue-comment template already carries a role's questions as the role wrote them.

`board.md` stayed as it was. Every line in it holds for each session on its own: work goes on the board before it starts, an issue opens from the owner's request in whichever session hears it, and the end-of-turn check covers what that turn changed. Its `Backlog` line already ties moving a task to autonomy.md's pick, which is now the PM session's. In autonomy.md, scoping "Keep going" to the PM session keeps the Assistant from picking roadmap tasks. The start-of-turn check for merged PRs goes with it. The first attempt left git.md's cleanup when the owner says a PR merged to whichever session hears it, which the review rightly read as leaving both sessions cleaning up the same branches.

For the cleanup, PM's reading of the review was that the Assistant relays "merged" to the PM session, whose start-of-turn check cleans up, and that git.md's own trigger then applies to a session working alone. The second attempt kept that for the PM session's PRs and also gave the Assistant the cleanup of its own small asks' branches, which open issues and PRs under board.md, since the narrower reading would have left nobody to clean those up. It worded the split by which session created a branch; the third attempt replaced that wording with a split by whose work the PR is, as the paragraph after next explains, because a later PM session must also clean up an earlier one's roadmap branches. The git.md sentence points at assistant.md instead of restating the split, so the split lives in one place. autonomy.md's start-of-turn line needed no change: it already sits under "These bind the PM session" and covers the roadmap's PRs, which are PM's. For the model check, the coordinator's `CLAUDE.md` keeps the ID's place and the `claude-opus-*` comparison, which are Claude mechanics, and the action on a mismatch stays only in `RULES.md`, as docs.md's three-file split asks.

In the third attempt, git.md's step-by-step rule that only "a branch a session created for a task's PR" is cleaned up without confirmation stayed word for word, as PM asked. Its pointer sentence instead says that a roadmap PR's branch counts as created by the PM session, whichever PM session created it, so a reader of git.md alone does not take an earlier PM session's branch for "a branch someone else made". That clause restates one fact of assistant.md's split, which lives there in full; leaving it out would have kept git.md's own lines disagreeing with assistant.md, the clash the review found. The alternative of rewording git.md's cover line itself to "a branch of a task's PR the session owns" would have changed the safety line the note asked to keep intact.

In the fourth attempt, the PM session's pushes follow the handbook rather than git.md, because the handbook binds the coordinator and HR's rules forbid loosening a git limit the owner's note does not name; #81 does not ask for the owner-asks exception. The Assistant is no department role, so git.md's Safety stays its rule. The review's other option, adding the exception to the handbook's Git section, would be a handbook change outside #81. The sentence names the two rules and links them instead of restating git.md. The Claude-note parenthesis copies the overview's "among the departments" so the two lines read the same.

The handbook's Git line, "Only PM ... runs `gh`", and PM's rule that only PM writes to GitHub on a task's behalf were left unchanged. Both bind department roles, the Assistant is none, and the departments' Claude notes already make department rules reference for any other session; direct sessions ran `gh` under `board.md` before this change too. The overview's Safety line, which describes rather than binds, was narrowed instead, since it read as covering every session. The Assistant's comments start with `🤖 Assistant:` because a relay that quotes the owner must not read as the owner's own comment, the reason the handbook gives every role its prefix. The line that at most one PM session runs at a time follows from the coordinator's one-task-at-a-time rule rather than adding one. The fresh-worktree facts went into the coordinator's Claude notes, because they are mechanics for the PM session, and the PM session reads that folder.

In the fifth attempt, the line that the PM session works in a worktree of its own stayed, while the line about the Assistant in it went. The worktree had been there to keep the Assistant's small asks from moving PM's branch, which no longer happens, but it still keeps the PM session's branch switches out of the owner's own checkout, and that is how the PM session is started today and what the coordinator's Claude notes on a fresh worktree assume. The alternative, running the PM session in the owner's checkout, would have removed the worktree cases from git.md's cleanup but would have moved branches under any work the owner leaves there, and since the PM session already runs in a worktree, the rule would no longer have described how it works. That reason is HR's reading, not the owner's words, so it is flagged for PM. With the Assistant out of git, the steps that still fail are the ones that touch a branch an ended PM session's worktree still has checked out: step 3's `git branch -d` when that worktree holds the merged branch, and step 2's `git checkout develop` and Branching's `git fetch origin develop:develop` when it holds `develop`, which step 2 itself leaves checked out in a PM session that ends without branching a next task. The fifth attempt covered only the first and wrongly said step 2 needed no change; the sixth covers all three, as below. The cleanup now covers every PR a PM session opened rather than "the roadmap's PRs", since every PR now comes from a PM session and owning the branches means cleaning all of them up; it still covers only task PRs' branches, as git.md's cover line requires. The confirmation line names a push to `master` beside `develop`, since the handbook already keeps both from every role and the Assistant pushes nothing. It applies only "where a rule lets a step happen" on the owner's confirmation, so it allows nothing a stricter rule forbids, such as the handbook's ban on history rewrites for the coordinator. It lives in assistant.md, the workspace rule both sessions read, and the coordinator's rules link to it instead of saying it again. `autonomy.md`, `board.md` and `delegation.md` were read for lines that no longer fit and needed no change: "Keep going" already binds only the PM session, board.md's lines hold for the Assistant's filed issues, and delegation.md's small-asks line no longer comes up for the Assistant, which assistant.md now says.

In the sixth attempt, of the Architect review's two ways out of the worktree clash, the next PM session removes an ended one's worktree, rather than each PM session removing its own when it ends. PM chose that way, and it holds even when a session ends without warning, as when the owner closes it or it stops mid-run, where a rule on how a session ends would not run at all; it also spares a session from removing the worktree it is running in. Reusing one standing worktree for every PM session, the HR review's other way, would change how the PM session is started, which is the owner's call. The removal sentence lives once, in assistant.md's worktree line, because worktrees of PM sessions exist only under that rule, and git.md's two places point at it, so the condition and the `--force` limit are written once. The owner gave "force-push this branch" as his own example of an exact action, but it could not stay the rule's example, since that line only applies where a rule lets the step happen on confirmation, and for the PM session none does. Saying so outright, rather than only swapping the example, answers the review's point that the old line read as allowing it.
