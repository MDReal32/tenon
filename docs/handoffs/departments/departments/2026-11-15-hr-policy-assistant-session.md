# The Assistant and the PM session, written as a rule change

[#81](https://github.com/MDReal32/tenon/issues/81) splits the owner's main session in two. Until now every department run happened inside the session the owner chatted with, so the owner could not talk to it while the pipeline ran. The owner's fix is the Assistant, the owner's chat session, which stays free to talk, and a PM session of its own that runs the pipeline, started by the Assistant and never asking the owner anything in chat. The owner wanted this as a workspace rule or a part of the structure, not a department. This is HR's write step on the rule-change route, under the [departments](departments.md) job, continuing [HR's role-effort handoff](2026-11-13-hr-policy-role-effort.md), the last rule change HR wrote. A second assignment on the same PR then asked HR to fix the five findings of the fresh HR run's owner review, as the second attempt of the write step, and a third asked it to fix the one finding of the second owner review, as the third and last attempt, so this handoff covers all three.

## Why this way

The model check is the one place where PM's account and the coordinator's rules disagreed. The account had a PM session on the wrong model say so and carry on, while the coordinator's notes had it ask for `/model` and stop. The stop wins. HR's rules forbid loosening the model check unless the owner's note asks for it in its own words, and #81 only asks who sets PM's model. Carrying on would also break the handbook's start-up check, which says a mismatch means no work. What changes is only where the report goes: to the Assistant, in the first line, since PM no longer asks the owner directly. PM's account also says it posts its questions in BA's plain-language shape with a suggested answer each. That stayed out, because the issue asks only that questions go on the issue, and the coordinator's issue-comment template already carries a role's questions as the role wrote them.

`board.md` stayed as it was. Every line in it holds for each session on its own: work goes on the board before it starts, an issue opens from the owner's request in whichever session hears it, and the end-of-turn check covers what that turn changed. Its `Backlog` line already ties moving a task to autonomy.md's pick, which is now the PM session's. In autonomy.md, scoping "Keep going" to the PM session keeps the Assistant from picking roadmap tasks. The start-of-turn check for merged PRs goes with it. The first attempt left git.md's cleanup when the owner says a PR merged to whichever session hears it, which the review rightly read as leaving both sessions cleaning up the same branches.

For the cleanup, PM's reading of the review was that the Assistant relays "merged" to the PM session, whose start-of-turn check cleans up, and that git.md's own trigger then applies to a session working alone. The fix keeps that for the PM session's PRs but words it as "each session cleans up only the branches it created". The narrower reading would have left nobody to clean up the branches of the Assistant's own small asks, which open issues and PRs under board.md, and git.md's cleanup already covers only a branch a session created for its task's PR. The git.md sentence points at assistant.md instead of restating the split, so the split lives in one place. autonomy.md's start-of-turn line needed no change: it already sits under "These bind the PM session" and covers the roadmap's PRs, which are PM's. For the model check, the coordinator's `CLAUDE.md` keeps the ID's place and the `claude-opus-*` comparison, which are Claude mechanics, and the action on a mismatch stays only in `RULES.md`, as docs.md's three-file split asks.

In the third attempt, git.md's step-by-step rule that only "a branch a session created for a task's PR" is cleaned up without confirmation stayed word for word, as PM asked. Its pointer sentence instead says that a roadmap PR's branch counts as created by the PM session, whichever PM session created it, so a reader of git.md alone does not take an earlier PM session's branch for "a branch someone else made". That clause restates one fact of assistant.md's split, which lives there in full; leaving it out would have kept git.md's own lines disagreeing with assistant.md, the clash the review found. The alternative of rewording git.md's cover line itself to "a branch of a task's PR the session owns" would have changed the safety line the note asked to keep intact.

The handbook's Git line, "Only PM ... runs `gh`", and PM's rule that only PM writes to GitHub on a task's behalf were left unchanged. Both bind department roles, the Assistant is none, and the departments' Claude notes already make department rules reference for any other session; direct sessions ran `gh` under `board.md` before this change too. The overview's Safety line, which describes rather than binds, was narrowed instead, since it read as covering every session. The Assistant's comments start with `🤖 Assistant:` because a relay that quotes the owner must not read as the owner's own comment, the reason the handbook gives every role its prefix. The line that at most one PM session runs at a time follows from the coordinator's one-task-at-a-time rule rather than adding one. The fresh-worktree facts went into the coordinator's Claude notes, because they are mechanics for the PM session, and the PM session reads that folder.
