# How the roster was finished, from Docs to HR, and the first rule change through HR

These ten handoffs are the second stretch of the [departments](departments.md) job, from 2026-11-06 to 2026-11-13, after [the departments foundation](2026-11-03--2026-11-06-compacted-departments-foundation.md). They write the four departments still missing from the roster, each in the shape Programming set: Docs for [#13](https://github.com/MDReal32/tenon/issues/13), DevOps for [#14](https://github.com/MDReal32/tenon/issues/14), Cyber security for [#15](https://github.com/MDReal32/tenon/issues/15) and HR for [#16](https://github.com/MDReal32/tenon/issues/16), each written by a direct session and checked by the Architect reviewer's rule review. They end with [#61](https://github.com/MDReal32/tenon/issues/61), the first rule change after HR existed, which names the root git and package-manager files in two roles' parts. Its session draft and the Architect's review of it are folded here; HR's own record of the task, [HR's root-file handoff](2026-11-13-hr-policy-root-file-owners.md), is newer and stays outside the fold.

## What was built

For #13, [`docs/departments/docs/`](../../../departments/docs/README.md) got its triplet, a knowledge file, the Docs report template and the writer role on Sonnet with an agent file, `docs-writer`, in Programming's shape. The writer documents what the approved plan and the change on the task branch say, stops and reports when a page and the code disagree, and moves a decision from still open to decisions only when the task records the owner's decision. Its part is the design book, `docs/tenon.md` and its six chapters, and every `README.md` outside `docs/`, the root one included. It never touches code, tests, schemas, config, a ruleset, a department file, a workspace rule or a work-record template. Programming's and QA's rules now give the writer exactly that part instead of every page under `docs/`. The Docs report may come with no commits when nothing needed to change.

For #14, [`docs/departments/devops/`](../../../departments/devops/README.md) got its triplet, a knowledge file and the engineer role on Opus with Programming's tools, as the agent file `devops-engineer`. It builds the release pipeline and the launchers, reviews CI, Nx and build config when the gate names it, and handles every request that needs `.env`. Its rules keep `.env` to the variables PM's request names, keep every secret value out of everything but `.env`, keep `.env.example` in step with placeholders, name CI secrets from the repository's store without holding them, and check with `git ls-files .env` that `.env` is untracked before every commit. Its part is `dist/`, the release workflow, `.env` and `.env.example`; releasing stays with the owner. It has three templates: the DevOps report, which never holds a secret value, the DevOps review, which checks that `.env.example` lists every variable a change reads, and the [DevOps analysis](../../../departments/devops/templates/devops-analysis.md) for its specialist step on the feature route. The overview's flow and PM's feature and small-change routes name the build step as the Programming or DevOps role for each part touched. The two "until DevOps is written" clauses, in the overview's safety section and the handbook's secrets section, and the two in Architect's rules are gone. The hook already allowed `.env` only to the exact agent type `devops-engineer`; its tests now prove "only" against `programming-engine` and four near-names (`devops`, `devops-reviewer`, `Devops-engineer`, `devops-engineer-2`), 168 tests in all.

For #15, [`docs/departments/cyber-security/`](../../../departments/cyber-security/README.md) got its triplet, a knowledge file, the Cyber security review template and the reviewer role on Opus with `Read`, `Grep` and `Glob`, as the agent file `cyber-security-reviewer`, which copies `architect-reviewer`'s. It is read-only and runs no commands, reviews only what the gate names it for, and judges security only against the design book's pages on runtimes, discovery and trust, the manifest and the decisions. Every review goes through a trust-boundary checklist: capabilities only as the manifest declares and the host enforces, WASM sandboxed by default, `exec` only for allow-listed binaries shown in the output and in `--dry-run` with no shell interpolation, every operation inside the generated project, process extensions shown as running with the user's privileges, checksums and signatures checked where the design asks, with what a failed check does left to the owner, and the access hook keeping its `.env`, `git` and `gh` limits with tests. A finding never holds a working exploit, and the template answers "not touched" for checks a change doesn't reach. The gate now names Cyber security for the access hook, and Architect's rules pass Cyber security notes to it.

For #16, [`docs/departments/hr/`](../../../departments/hr/README.md) got its triplet, a knowledge file, the HR report and HR review templates, and the policy role on Opus with `Read`, `Grep`, `Glob`, `Edit`, `Write` and `Bash`, as the agent file `hr-policy`. Its part is everything under `docs/departments/`, the agent files, the workspace rules under `.claude/rules/`, and the access hook with its tests and its wiring in `.claude/settings.json`. A rule change carries out only the owner's note, a retro's proposal or a parked role gap; it never decides a design item, never loosens a safety rule unless the owner's note asks in its own words, keeps the three levels and the three-file split, and comes with a test for every call a hook change newly allows or denies. A fresh HR run gives the owner review. PM's coordinator gained the rule-change route: HR policy, a fresh HR run as owner review, the Architect reviewer's rule review, and Cyber security when the hook changes, with the task branch created at intake and the draft PR opened after HR's first report. Cyber security's rules take a hook-changing rule-change PR when PM hands one over, and send a change no plan named back to the HR run that wrote it. The retro's proposal runs as a rule change through HR, the overview's role-gap bullet asks the owner first as PM's rules do, and the handbook says rules change through HR. Every "until HR is written" clause is gone, and the overview says every department is written. The small-change route's older branch gap went to [#58](https://github.com/MDReal32/tenon/issues/58) in `Backlog`.

For #61, carrying out the owner's answer on [#17](https://github.com/MDReal32/tenon/issues/17), a direct session drafted the change and the Architect reviewer reviewed the draft, which clashed on process only: rules change only through HR. The session took the draft out of the working tree and left it in its handoff for HR, which wrote the change in commit `7dd84e2` once [#62](https://github.com/MDReal32/tenon/issues/62) let it pass the start-up check, as [HR's root-file handoff](2026-11-13-hr-policy-root-file-owners.md) records. The DevOps engineer's part now names `.gitignore` and `.gitattributes`, and the Programming dev role's names `Cargo.lock`, `.yarnrc.yml` and `.yarn/`, with the READMEs and the overview's roster following and the roster table re-aligned. The Architect reviewer's attempt 2 found the process clash settled and no new clash.

## Decisions

Each department after Programming copies the closest existing shape: Docs and HR follow Programming's for departments that write files, DevOps follows Programming's tools on Opus, and Cyber security follows Architect's for a read-only reviewer, as "Adding a department" says. While HR wasn't written, a direct session wrote each department and the Architect reviewer's rule review checked it; from #61 on, rules change only through HR, and neither PM nor a direct session may do HR's step or stand in for its owner review.

The writer's part leaves out `docs/departments/`, `docs/handoffs/` and `docs/templates/`, though they sit under `docs/`, because rulesets change through rule-change PRs and the work record belongs to the role that writes it. The writer documents rather than designs, because a page that settled an open question would be a design decision the gate and the owner never saw. It takes every `README.md` outside `docs/` rather than only those under the four package roots, because the roster gives Docs package READMEs without exceptions and a README under `dist/` or `protocol/` would otherwise have no owner; the Architect reviewer accepted this wider part over the narrower attribution it first suggested, since the ownership is the owner's call. The docs check is left to `libs/dev`, with reading the links as the fallback.

The roster gave DevOps "CI, `libs/dev` tooling and build config" while Programming's dev role already owned them. The code stayed with the dev role, with DevOps as its reviewer, and DevOps took only the release workflow among the workflows, so every file has one owner and PM's routing of findings stays simple. Environment variables went into DevOps' review rather than off the gate's list, since the variables a change reads are where a secret could slip into a commit. DevOps got its own specialist step rather than making the step depend on the owning department, which keeps PM's feature route the same for every department. The engineer runs on Opus because its work is judgment about secrets and releases, not volume, and releasing stays with the owner because publishing can't be undone. The commit check uses `git ls-files .env`, because `git status` never lists an ignored file. The hook trusts the agent type alone, so a session started with `claude --agent devops-engineer` also reaches `.env`; that matches the rule's intent.

The access hook joined Cyber security's scope because #14 had the owner review the hook standing in for Cyber security; leaving it off the gate's list would leave the hook with no reviewer. Secrets in CI, the release and `.env` stay DevOps', so the two reviews don't overlap. Cyber security has no specialist or build step, because it owns no part of the repository and a security concern before the build is the gate's. The signing check first said a failed check stops the install, which decided an open design item; it now leaves what a failure does to the owner. The checks that go beyond the design's words, no shell interpolation in `exec` and no path outside the generated project, follow from decision 3's rule that extensions only emit operations and from M0's overwrite guard; they check how the design is built rather than add design.

HR's part takes the workspace rules because the roster gives HR every ruleset and leaving `.claude/rules/` out would leave the rules every role follows with no owner. It takes the access hook because "Adding a department" changes the hook with a role that needs a new privilege and HR adds roles; the hook is small and its tests are its spec, so it needs no Programming role, and Cyber security reviews every change to it. That is why HR has `Bash`. Knowledge files sit in HR's part for their facts, while each department's lessons stay its own work record. The rule-change route had to be added to PM, because a department no route reaches can't run, the lesson DevOps' review taught and HR's knowledge file records. In rule reviews, the Architect reviewer counts as a clash any gap where one ruleset gives a role work another gives it no way to do, and fixes narrow a rule and loosen nothing.

For #61, the parts name exact files rather than the owner's categories, so a role can tell from its rules alone whether a file is its own. `.gitattributes` was drafted next to `.gitignore` because both are git's own root files and generated files will be marked `linguist-generated` there. The session removed its draft rather than committing it, which keeps PM to committing only the work record and lets HR write the change as its own work.
