# Departments

The departments are how Tenon's work is meant to be done: AI agents organized like a company's departments, each with a written ruleset, taking a task from the owner through a brief, a gate, the build and the reviews to a pull request. This job covers the rulesets themselves, the agent files that load them, the hook that enforces their access rules, and the record every piece of work leaves behind.

## How it works

The [departments overview](../../../departments/README.md) holds the idea, the roster, the flow and the safety rules, and the [handbook](../../../departments/RULES.md) holds the rules every role follows. All ten departments are written: PM, whose coordinator runs in a session of its own that the Assistant, the owner's chat session, starts; BA, whose assistant checks a task against the definition of ready; PO, whose proxy judges product fit at the gate; Architect, whose gate and reviewer judge technical fit against [the design book](../../../tenon.md) and its four axes; Programming, whose engine, sdk, extension and dev roles build the code and its tests, each in its own part of the repository; QA, whose conformance and e2e roles check the change from the outside and write only a bug's reproduction test, never product code; Docs, whose writer keeps the design book and the package READMEs true to the change, never code; DevOps, whose engineer builds the release and the launchers, reviews CI and build config, and alone handles `.env`; Cyber security, whose reviewer checks every change the gate names it for against Tenon's trust boundary and the access hook, never editing; and HR, whose policy role writes and reviews every rule change, the workspace rules and the access hook included. Every role but the coordinator has an agent file under `.claude/agents/`, and a project hook under `.claude/hooks/department-access` blocks `.env` for everyone but the DevOps engineer, and keeps branching, pushing and `gh` with the sessions that run without an agent type, PM's and the Assistant's. The work record follows `.claude/rules/handoffs.md`, with notes started from `docs/templates/`.

Every route now has a department for each step, so a task can run through the pipeline end to end.

## How it got here

The first stretch, from the first four departments, the workspace rules and the hook through the tracker, the board's statuses, the board rule, Programming, the autonomy rules and QA, is folded into [the departments foundation](2026-11-03--2026-11-06-compacted-departments-foundation.md). It was shaped after a sibling project's department system but written for Tenon alone. The second stretch, Docs, DevOps, Cyber security and HR, each written by a direct session and checked by the Architect reviewer's rule review, then the first rule change after HR existed, the root-file owners, is folded into [the roster compaction](2026-11-06--2026-11-13-compacted-departments-roster.md).

[#69](https://github.com/MDReal32/tenon/issues/69), through [HR's role-effort handoff](2026-11-13-hr-policy-role-effort.md), gives every agent file a reasoning `effort` and adds an "Effort" section to `.claude/rules/delegation.md` naming when PM sets a different effort for one run, with `max` never used; `hr-policy` wrote it and fixed, in attempt 2, what HR's owner review and the Architect rule review found in the delegation rule; both reviews approved attempt 2, and it merged in PR 70. [#81](https://github.com/MDReal32/tenon/issues/81), through [HR's Assistant handoff](2026-11-15-hr-policy-assistant-session.md), splits the owner's chat from the pipeline with a workspace rule, `.claude/rules/assistant.md`. The Assistant is the owner's chat session, not a department; it is the only session that asks the owner in chat, and starts the PM session, where the coordinator now runs and asks its questions only on the issue and in its report. `hr-policy` wrote it, and in attempt 2 fixed the five findings of HR's owner review: pushes to `develop` and `master` follow git.md's Safety section, the Assistant starts PM as a separate session in a worktree of its own, and after a merge each session cleans up only the branches it created. The second owner review found those five fixed and one new clash: tying the cleanup to the session that created a branch left a later PM session unable to clean up an earlier one's merged roadmap branches without the owner's confirmation. Attempt 3, the last, splits the cleanup by whose work the PR is: the running PM session cleans up every roadmap PR's branch through autonomy.md's start-of-turn check, as its own, and the Assistant only those of its own small asks, with git.md's pointer saying the same. HR's third owner review approved attempt 3 with no findings. The Architect rule review then found three clashes. Attempt 4 fixed two of them: the Assistant pushes to `develop` and `master` only as git.md's Safety allows, while the PM session never pushes to them, as the handbook says; and the departments' Claude notes now say the hook keeps `gh` with PM among the departments, as the overview already did. The owner's answers then settled the remaining clash, how git.md's cleanup runs from a worktree, and the question of relayed confirmations. Attempt 5 rewrote the rule for them. The Assistant does no task: it keeps and polishes the owner's ideas, says where things stand, files work for the departments as issues on the board and messages the PM session, and uses `gh` only for issues and their board items. The PM session owns the branches and `develop` and does every after-merge cleanup. A relayed message confirms a destructive step only when it quotes the owner's words naming that exact action, and a merge or a push to `develop` or `master` stays the owner's. HR's fourth owner review of attempt 5 found that removing an ended PM session's worktree only before deleting the merged branch missed `develop`, which cleanup step 2 leaves checked out in that worktree, so the next PM session's `git checkout develop` and `git fetch origin develop:develop` would fail. The Architect's second rule review found the same, plus two clashes: the confirmation line's "force-push this branch" example, though the handbook keeps every history rewrite from every role, and "the only session that asks the owner questions", though PM asks on the issue. Attempt 6 fixed all three: the PM session removes an ended PM session's worktree that has `develop` or the merged branch checked out before cleanup step 2 and before branching, written once in assistant.md's worktree line, with git.md pointing at it from both places; the confirmation example is now deleting an unmerged branch, and no relay lets the PM session force-push or rewrite history; and the Assistant is the only session that asks the owner in chat. A fresh HR owner review and the Architect reviewer's third rule review of attempt 6 both found nothing, so [#81](https://github.com/MDReal32/tenon/issues/81)'s PR is ready for the owner's review.
